## Pré-vol (à faire AVANT l'exposé, pas pendant le chrono)

- `npm start` ou `docker compose up --build`, UI sur `http://localhost:3009` ; deux fenêtres déjà ouvertes, ACME sélectionné, deux JWT **créés après le dernier redémarrage** (clé aléatoire par processus), connexion Socket.IO active. Vérifier présence 2 et séquences qui avancent.
- Onglets GitHub déjà ouverts sur run vert, PR rouge, step `Gate`, finding Security avec **filtre branche `demo/red-sast`** ; maintenir la PR ouverte, **ne pas la fusionner**. Les derniers runs de docs peuvent être encore en file : utiliser le run vert effectivement terminé, pas un statut supposé.
- Pour la démo du « piège » indépendant du navigateur : `npm run scenario` doit diverger (exit 1), `npm run scenario -- --avec-strategie` converge (exit 0). Le garder en **preuve de secours** si le bouton UI ne marche pas, pas comme un sixième écran.
- Capturer localement les deux fenêtres synchronisées et les runs GitHub horodatés **si** la soutenance autorise un mode backup ; ces captures ne sont **pas encore créées**. Si le lancement échoue, maximum 2 min avant le backup selon les grilles. Vérifier la veille que les liens GitHub s'ouvrent sur le poste de soutenance.

## Q&A — quatre questions à expliquer sans lire

1. **[F] Pourquoi SSE pour les prix et Socket.IO pour les bids ?** Un flux serveur→navigateur vs des commandes bidirectionnelles avec ack et rooms ; les deux ont des frontières différentes.
2. **[F] Que signifient seq, `Last-Event-ID` et le buffer de 50 ?** Petit trou : tous les ticks manqués sont rejoués ; grand trou : instantané, état courant correct mais historique intermédiaire non récupéré.
3. **[C] Le navigateur se reconnecte après un redémarrage du serveur : que garantit-on ?** Rien de durable : clé et buffers en mémoire sont renouvelés, vieux JWT invalides par défaut, bids perdus ; nouvel instantané et nouvelle authentification pour la démo.
4. **[C] Pipeline vert : un visiteur peut-il se faire passer pour Alice ?** Oui, `/api/auth/token` signe le nom choisi ; Semgrep a corrigé le secret embarqué, pas l'identité. Quelle frontière du DFD manque-t-il ? Vérification avant émission du token.

## Ce que le jury pourrait contester

- La sécurité prévoit **2 min risque + 3–4 min CI + 2 min décisions** ; ici ces parties ne prennent que 3 min ensemble. Les deux grilles prises littéralement ne tiennent pas en une seule présentation de 9 min. Demander explicitement si un **passage commun de 12–14 min** est autorisé ou si le jury accepte la version comprimée avec annexes.
- « Introduire une régression préparée » : la PR est réelle mais déjà exécutée. Si le jury exige de la provoquer devant lui, un rerun peut prendre plusieurs minutes/être en queue ; prévoir de montrer le commit et le run rouge existant sans promettre un build immédiat.
- La présence ne compte que les spectateurs avec JWT, pas les lecteurs SSE anonymes ; le bouton ferme SSE 3 s mais **pas** Socket.IO, donc la présence ne doit pas tomber pendant cette coupure.
